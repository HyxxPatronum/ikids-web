总判定

项目不是“很多重复文件都能删”，而是一个正在从静态原型迁移到 React/Cloudflare 架构的混合仓库。静态页面仍承担课程目录、完整学习活动、账号和内容工作台；React 当前主要承担词汇中心、段落查词与共享查词抽屉。

可以先清约 740 MB 的依赖和构建产物，但业务文件只建议在确认历史数据后再删。

最安全的清理对象是 node_modules/、dist/、.next/、.vinext/、test-results/ 与 tsconfig.tsbuildinfo。public/ 的九个镜像文件可由构建重建，但 public/og.png 是唯一源文件，必须保留。.wrangler/ 包含本地 D1/R2 状态，删除会清空本地云资源模拟数据。

    发现的结构风险

    这些不是本次要求修复的问题，但会直接影响后续清理。优先消除“两个事实来源”比继续删零散文件更有价值。

    数据库 schema 双轨

    db/schema.ts + drizzle/ 是实际迁移链。 db/schema.sql 仍描述 users、sessions 和旧进度字段，却缺少当前 cards.slug、media_json、staging 等实际字段。建议把 SQL 文档改为从 Drizzle 生成，或明确标成历史参考后删除。

    旧本地 JSON 数据源已脱离运行时

    data/app-db.json 和 data/series.json 没有当前代码引用。 文档仍称 app-db 是本地开发数据源，但 API 已只绑定 D1。先确认其中用户进度与内容是否已迁移，再归档或删除，并同步文档。

    public 是“镜像 + 唯一资产”混合目录

    九个文件由根目录复制，og.png 却只有 public 版本。 因此不能把整个目录当缓存删掉。更清晰的做法是把静态源集中到 public，或把生成镜像放到纯构建目录。

    前端迁移尚未完成

    静态 HTML 仍是核心业务面，不是遗留垃圾。 ADR 明确选择渐进迁移；若未来全部迁入 React，应该以路由与 E2E 覆盖为删除门槛，而不是按文件年代清理。
